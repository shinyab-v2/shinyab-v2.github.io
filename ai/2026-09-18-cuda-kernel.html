CUDA / Custom Operator
Tensor 연산을 GPU Thread까지 내려보기

PyTorch operator 아래에서 GPU가 실제로 어떻게 병렬 작업을 나누는지 thread, block, grid, memory hierarchy 관점으로 내려갑니다.

1. CPU loop를 GPU 관점으로 바꾸기

# CPU 사고방식
for i in range(N):
    y[i] = relu(x[i])

GPU에서는 N개의 element를 여러 thread가 나눠 처리하도록 설계합니다. 대표적인 1D indexing은 idx = blockIdx.x * blockDim.x + threadIdx.x입니다.

2. CUDA kernel의 기본 형태

__global__ void relu_kernel(const float* x, float* y, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) y[i] = x[i] > 0.f ? x[i] : 0.f;
}

__global__ 함수는 host에서 launch되고 device에서 실행됩니다. 실제 custom op에서는 dtype, contiguous 여부, shape, device check 등 훨씬 많은 검증이 필요합니다.

3. Grid / Block / Thread

threads = 256
blocks = (N + threads - 1) / threads
relu_kernel<<<blocks, threads>>>(x, y, N)

256은 보편적인 예시이지 항상 최적이라는 뜻은 아닙니다. occupancy, register 사용량, workload 특성을 profiler로 확인해야 합니다.

4. Memory hierarchy

Global memory는 크지만 상대적으로 비싸고, register는 매우 빠르지만 thread별 자원이 제한됩니다. shared memory는 같은 block의 thread가 데이터를 재사용할 때 유용합니다. custom kernel 최적화에서 FLOPs보다 memory access가 병목인 경우가 많습니다.

5. Coalesced access

인접 thread가 인접 memory address에 접근하도록 하면 global memory transaction을 효율적으로 만들 수 있습니다. Tensor layout(NCHW/NHWC)과 indexing 순서가 성능에 영향을 주는 이유입니다.

6. PyTorch custom op 연결

실전에서는 C++/CUDA extension 또는 custom operator registration을 통해 PyTorch Tensor와 CUDA kernel을 연결합니다. forward만 필요한 inference op와 backward까지 필요한 training op의 구현 범위도 다릅니다.

7. Grid Sample과 연결

grid_sample 같은 연산은 output pixel마다 source coordinate를 읽고 주변 pixel을 interpolation합니다. 이때 boundary handling, align_corners, interpolation mode가 numerical correctness를 좌우합니다. TensorRT plugin을 만들 때도 PyTorch reference와 element-wise 비교가 필수입니다.

검증 원칙: custom CUDA는 빠른 것보다 먼저 reference implementation과 동일해야 합니다. 작은 deterministic tensor → edge case → random tensor → performance 순으로 검증하세요.

8. 성능 측정

CUDA event 또는 profiler를 이용하고 warm-up과 synchronization을 포함합니다. kernel만 측정하는지 host-device copy까지 포함하는지도 명시합니다.

9. Ultrasound AI

고해상도 ultrasound에서 custom preprocessing, resampling, postprocessing이 전체 latency의 상당 부분을 차지할 수 있습니다. network만 TensorRT로 빠르게 만들고 CPU 후처리를 방치하면 end-to-end latency 개선이 제한될 수 있습니다.

10. 실습

  1. element-wise ReLU kernel의 thread index를 손으로 계산합니다.
  2. N=1000, block=256일 때 block 수와 마지막 block의 유효 thread 수를 계산합니다.
  3. contiguous/non-contiguous tensor 차이를 확인합니다.
  4. reference PyTorch output과 custom op max absolute error를 비교합니다.
  5. Nsight/torch profiler 관점에서 memory-bound인지 생각해봅니다.

11. 복습 문제

  1. block 안 thread가 공유할 수 있는 빠른 memory는? shared memory.
  2. 왜 bounds check가 필요한가? 마지막 block의 thread가 N을 넘을 수 있기 때문이다.
  3. thread 수 256이 항상 최적인가? 아니다.
  4. custom op에서 가장 먼저 검증할 것은? numerical correctness.
  5. GPU kernel이 빨라도 end-to-end가 느릴 수 있는 이유는? copy/전후처리/동기화가 병목일 수 있다.
