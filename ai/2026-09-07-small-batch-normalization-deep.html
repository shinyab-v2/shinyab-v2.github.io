1. Normalization을 Tensor 축으로 이해하기

입력이 x.shape = [N, C, H, W]라고 합시다. Normalization layer의 핵심은 “어떤 축에서 평균과 분산을 모으는가?”입니다. 이름을 외우기보다 통계 집합을 생각하면 BN·GN·LN의 차이가 명확해집니다.

Layer통계 범위Batch size 영향running stats
BatchNorm2d각 C에 대해 N,H,W직접 영향기본 설정에서 사용
GroupNorm각 sample 내부 channel group,H,W직접 영향 없음없음
LayerNormnormalized_shape로 지정한 마지막 축직접 영향 없음없음

1.1 Feature 채널은 RGB 색상 채널과 다르다

입력 채널은 RGB 3개 또는 흑백 초음파 1개처럼 물리적인 색상/신호 성분입니다. 반면 첫 Convolution을 통과한 뒤의 C는 서로 다른 학습된 필터의 반응 지도(Feature Map) 수입니다. 초기 채널은 경계·질감 등의 국소 패턴에 반응하고, 깊은 층에서는 결합된 형태와 의미적 특징을 표현할 수 있습니다. 다만 “0번 채널=수평 경계”처럼 고정적인 채널 의미는 보장되지 않습니다.

nn.Conv2d(32, 64, 3) (기본 groups=1)의 Weight Shape는 [64, 32, 3, 3]입니다. 출력 채널 하나는 입력 채널 하나와 1:1 대응하지 않고 32개 입력 Feature 채널을 함께 결합합니다. GN의 그룹 역시 채널의 의미를 인식해 자동 분류하는 것이 아니라 채널 인덱스 순서로 나눕니다.

2. BatchNorm2d — train과 eval은 다른 시스템이다

BatchNorm의 개념식은 다음과 같습니다.

y = gamma * (x - mu) / sqrt(var + eps) + beta

gamma와 beta는 channel별 학습 가능한 affine parameter입니다. 중요한 것은 mu, var가 train/eval에서 어디서 오는가입니다.

model.train()
# current mini-batch statistics 사용
# running_mean / running_var 업데이트

model.eval()
# 저장된 running_mean / running_var 사용

왜 small batch가 문제가 될 수 있는가?

BN 통계는 N만 보는 것이 아니라 N×H×W 위치에서 모이므로 “batch=2이면 무조건 실패”처럼 단순화할 수는 없습니다. 그러나 sample 간 영상 분포가 크게 다르거나 spatial map이 작은 late stage, 강한 augmentation, device/vendor가 batch마다 달라지는 환경에서는 mini-batch 통계가 training distribution을 불안정하게 대표할 수 있습니다.

‘튀는 이미지’를 평준화한다는 뜻일까?

정확히는 정규화 통계를 다른 이미지와 공유하느냐의 문제입니다. BN의 학습 출력은 Batch 구성에 의존하므로 다른 장비의 밝은 영상이 함께 들어올 때 같은 이미지도 다른 값으로 정규화될 수 있습니다. GN과 LN은 각 샘플 내부에서 통계를 구하므로 직접적인 Batch 동료의 영향을 피합니다.

주의: GN/LN도 이미지 자체에 있는 극단적인 Feature·잘못된 라벨·심한 Artifact를 자동 제거하지 않습니다. 그 영상의 Loss와 Gradient는 여전히 학습에 영향을 줄 수 있습니다. 데이터 품질과 BN 통계 문제를 구별하세요.

실무 경고 신호
  • batch 16→2 변경 뒤 validation metric 급락
  • train mode inference와 eval mode inference 간 gap이 비정상적으로 큼
  • fine-tuning loss는 감소하지만 실제 inference 성능이 나쁨
  • GPU별 batch 구성에 따라 metric variance가 큼
  • vendor/device/protocol별 subgroup 성능이 크게 갈림

running_mean 업데이트를 직접 관찰

import torch
import torch.nn as nn

bn = nn.BatchNorm2d(4)
bn.train()

for step in range(5):
    # 매 step 분포를 의도적으로 바꿈
    x = torch.randn(2, 4, 8, 8) + step * 2
    _ = bn(x)
    print(step, bn.running_mean.detach().clone())

이 실습을 하면 current batch의 분포 변화가 running stats에 누적되는 것을 볼 수 있습니다. 실제 의료영상에서는 augmentation·기관·장비 배치가 이 역할을 할 수 있습니다.

3. GroupNorm — sample 내부에서 통계를 만든다

GroupNorm은 channel을 여러 그룹으로 나누고 sample별로 그룹 안의 통계를 계산합니다.

x = torch.randn(2, 32, 64, 64)
gn = nn.GroupNorm(num_groups=8, num_channels=32)
y = gn(x)
print(y.shape)  # [2,32,64,64]

num_channels % num_groups == 0이어야 합니다. “32 groups”를 규칙처럼 외우면 channel 24 같은 layer에서 바로 실패합니다.

def choose_groups(channels, preferred=8):
    for g in [preferred, 32, 16, 8, 4, 2, 1]:
        if g <= channels and channels % g == 0:
            return g
    return 1
GN의 중요한 특성: PyTorch GroupNorm은 train/eval 모두 현재 input 통계를 사용합니다. 따라서 GN 자체 때문에 train/eval normalization 정책이 달라지지는 않습니다. 단, Dropout 등 다른 layer가 있으면 전체 모델 출력은 여전히 달라질 수 있습니다.

3.1 LayerNorm도 Batch 축을 사용하지 않지만 GN과는 다르다

BN은 동일 채널의 N×H×W, GN은 각 이미지의 (C/G)×H×W를 정규화합니다. LN은 normalized_shape에 명시한 마지막 축을 정규화합니다. 이 때문에 Transformer [B,T,D]에서 LayerNorm(D)는 각 Token의 D개 Feature를 정규화하지만, CNN NCHW에서 LayerNorm((C,H,W))는 이미지마다 C·H·W 전체를 정규화합니다.

그림은 LN이 LayerNorm((C,H,W))인 경우입니다. 각 공간 위치의 채널만 정규화하려면 NHWC 변환 후 LayerNorm(C)를 사용합니다. GN의 G=1은 C·H·W에 대해 LN과 통계 범위가 비슷하지만, 기본 affine 파라미터 구성까지 동일하지는 않습니다.

import torch
import torch.nn as nn
x = torch.randn(2, 32, 64, 64)    # NCHW
gn = nn.GroupNorm(8, 32)            # 각 샘플의 4채널 그룹×H×W
ln_all = nn.LayerNorm((32, 64, 64))  # 각 샘플의 C×H×W
ln_channel = nn.LayerNorm(32)        # NHWC에서 마지막 C만
y = ln_channel(x.permute(0, 2, 3, 1)).permute(0, 3, 1, 2)
assert y.shape == x.shape

실무 해석: CNN Small Batch 문제라고 해서 LN을 우선 삽입하는 것은 아닙니다. 일반적으로 기존 아키텍처의 정규화 방식을 유지하고, 문제가 관측될 때 GN/Frozen BN 등을 비교합니다.

4. BN 유지 / Frozen BN / GN / SyncBN 선택

BN 유지

각 forward의 BN 통계 배치와 pretrained recipe가 안정적이라면 원형 유지가 가장 단순합니다. gradient accumulation의 유효 배치와는 다릅니다.

Frozen BN

pretrained running stats를 신뢰하고 작은 fine-tuning batch에서 통계 업데이트를 막고 싶을 때 절충안입니다.

GroupNorm

high-resolution detection/segmentation처럼 per-GPU batch가 작고 batch composition 영향이 큰 경우 강한 후보입니다.

SyncBatchNorm

DDP 여러 GPU의 BN 통계를 동기화해 effective batch를 늘릴 수 있지만 통신 비용과 deployment recipe를 고려해야 합니다.

5. PyTorch 모델의 BN을 GN으로 안전하게 재귀 교체

import torch
import torch.nn as nn

def choose_groups(channels, preferred=8):
    candidates = [preferred, 32, 16, 8, 4, 2, 1]
    for g in candidates:
        if g <= channels and channels % g == 0:
            return g
    return 1


def replace_bn_with_gn(module,
                       preferred_groups=8,
                       copy_affine=True):
    for name, child in list(module.named_children()):
        if isinstance(child, nn.BatchNorm2d):
            c = child.num_features
            groups = choose_groups(c, preferred_groups)
            gn = nn.GroupNorm(
                num_groups=groups,
                num_channels=c,
                eps=child.eps,
                affine=child.affine,
            )
            if copy_affine and child.affine:
                with torch.no_grad():
                    gn.weight.copy_(child.weight)
                    gn.bias.copy_(child.bias)
            setattr(module, name, gn)
        else:
            replace_bn_with_gn(
                child,
                preferred_groups,
                copy_affine)
    return module

왜 named_children 재귀인가?

Residual main path의 bn1/bn2뿐 아니라 projection shortcut, stem, decoder, FPN lateral block처럼 깊은 module hierarchy에 숨어 있는 BN까지 모두 찾기 위해서입니다. 일부만 교체하면 모델은 실행되더라도 normalization 정책이 섞입니다.

6. Checkpoint 호환성 — affine은 복사 가능, running stats는 불가

BN stateGN으로 이동설명
weight (γ)가능shape [C], GN affine과 대응
bias (β)가능shape [C], GN affine과 대응
running_mean불가GN에 해당 buffer 없음
running_var불가GN에 해당 buffer 없음
num_batches_tracked불가GN에 해당 buffer 없음

따라서 가장 안전한 순서는 원본 BN 모델에 checkpoint를 먼저 load → affine을 가진 BN 객체를 GN으로 교체하면서 γ/β copy입니다.

model = build_bn_model()
ckpt = torch.load('pretrained.pt', map_location='cpu')
model.load_state_dict(ckpt, strict=True)
model = replace_bn_with_gn(model, copy_affine=True)
주의: weight shape가 맞아서 load 가능하다는 것과 동일 inference 의미는 완전히 다른 문제입니다. BN의 running statistics가 사라지고 normalization statistics 계산 방식이 바뀌므로 반드시 fine-tuning과 validation이 필요합니다.

6.1 Fine-tuning 시 원래 없던 GN/LN을 삽입하면?

가능하지만 pretrained Weight의 이점을 보존한다고 보장할 수 없습니다. 기존 Conv 가중치는 재사용 가능하나, 정규화 레이어가 기존 Feature를 재계산하므로 후속 Layer가 받는 입력이 달라집니다. GN/LN에서 γ=1, β=0은 identity 함수가 아닙니다. BN→GN 교체에서도 BN γ/β 복사는 가능하지만 running_mean, running_var가 사라져 통계적 의미가 달라집니다.

Case A: 기존 BN → GN

원래 BN checkpoint를 먼저 로드한 후 GN으로 교체하면서 affine γ/β를 복사합니다. Conv Weight는 재사용되지만 BN의 pretrained running statistics는 쓰지 않습니다.

Case B: GN/LN 신규 삽입

기존 Conv는 그대로, 신규 γ/β는 새로 학습합니다. 원래 없던 정규화를 추가하면 Feature 분포가 변합니다. 구조 변경 실험으로 별도 평가해야 합니다.

실습: 같은 Conv Weight를 로드해도 출력은 달라진다

import torch
import torch.nn as nn

class TinyCNN(nn.Module):
    def __init__(self, add_gn=False):
        super().__init__()
        self.conv1 = nn.Conv2d(1, 32, 3, padding=1)
        self.norm = nn.GroupNorm(8, 32) if add_gn else nn.Identity()
        self.relu = nn.ReLU()
        self.conv2 = nn.Conv2d(32, 1, 3, padding=1)
    def forward(self, x):
        return self.conv2(self.relu(self.norm(self.conv1(x))))

torch.manual_seed(7)
old = TinyCNN(False).eval()
new = TinyCNN(True).eval()
result = new.load_state_dict(old.state_dict(), strict=False)

assert set(result.missing_keys) == {"norm.weight", "norm.bias"}
assert not result.unexpected_keys
assert torch.equal(old.conv1.weight, new.conv1.weight)
assert torch.equal(old.conv2.weight, new.conv2.weight)

x = torch.randn(2, 1, 64, 64)
with torch.no_grad():
    print("output MAE:", (old(x) - new(x)).abs().mean().item())

strict=False가 호환성을 자동으로 보장하지는 않습니다. Missing/Unexpected Key와 Weight shape을 확인해야 합니다. 레이어 교체 후 optimizer를 만들고, Feature 통계·Validation 성능을 비교해야 합니다. 선택적 실험으로 y=x+α(GN(x)-x)를 초기 α=0으로 두면 초기 함수가 identity가 되지만, 이 구조도 별도로 학습·검증해야 합니다.

핵심 판단: 작은 Batch라고 GN/LN을 기존 pretrained 네트워크의 중간에 새로 삽입하는 것을 기본값으로 삼지 않습니다. GN 삽입은 활성화 메모리와 계산 비용을 증가시킬 수도 있습니다.

7. Optimizer · DDP · freeze에서 생기는 숨은 버그

7.1 Optimizer는 layer 교체 뒤 생성

# BAD
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)
model = replace_bn_with_gn(model)

# GOOD
model = replace_bn_with_gn(model)
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-4)

새 GN module은 새로운 Parameter 객체를 만듭니다. 기존 optimizer가 교체 전 BN parameter를 계속 참조하는 상황을 피하려면 optimizer를 다시 만듭니다.

7.2 model.train()이 Frozen BN을 다시 train으로 바꾼다

fine-tuning loop에서 매 epoch model.train()을 호출하면 앞서 bn.eval()한 상태가 다시 train으로 돌아갑니다. Frozen BN을 원한다면 train mode 설정 뒤 BN만 다시 eval로 고정하거나 별도 FrozenBatchNorm 구현을 사용하는 방식이 필요합니다.

def set_bn_eval(m):
    if isinstance(m, nn.BatchNorm2d):
        m.eval()

for epoch in range(num_epochs):
    model.train()
    model.apply(set_bn_eval)
    ...

7.3 Gradient accumulation은 BN batch를 키우지 않는다

gradient accumulation으로 optimizer step의 effective batch는 커지지만 각 forward에서 BN이 보는 mini-batch 통계는 그대로입니다. 따라서 batch=2를 8 step accumulate해도 BN이 한 번에 16 samples의 통계를 계산하는 것은 아닙니다.

중요 구분: optimizer effective batch와 normalization statistics batch는 같은 개념이 아닙니다.

7.4 Gradient Accumulation은 BN 통계 Batch를 늘리지 않는다

2개 이미지로 4번 forward/backward하면 optimizer effective batch는 8이지만, BN은 매 forward에서 2개 이미지의 N×H×W를 이용해 통계를 계산합니다. Multi-GPU SyncBN은 같은 forward의 통계를 GPU 간 공유하지만 accumulation step의 통계를 합치는 것은 아닙니다. Batch의 Gradient Noise 문제와 BN Running Statistics 문제를 구분해야 합니다.

8. 직접 실행하는 4개 실험

Lab A — BN vs GN train/eval gap

@torch.no_grad()
def train_eval_gap(model, x):
    model.train()
    y1 = model(x).detach().clone()
    model.eval()
    y2 = model(x).detach().clone()
    return (y1 - y2).abs().mean().item()

Dropout 없는 작은 모델로 BN/GN을 비교해 normalization 정책 차이를 직접 확인합니다.

def count_norms(model):

        if isinstance(m, nn.BatchNorm2d): result['bn'] += 1
        if isinstance(m, nn.GroupNorm): result['gn'] += 1

    if p.requires_grad and p.grad is None:
        print('NO GRAD:', name)

모델은 실행되는데 새 GN parameter가 optimizer에 들어가지 않은 종류의 조용한 버그를 잡습니다.

9. 의료 초음파 프로젝트의 실험 설계

Breast lesion detection, lung ultrasound B-line/LUS, segmentation처럼 고해상도 입력을 쓰면 per-GPU batch가 작아지는 경우가 많습니다. 단순 전체 metric만 비교하면 normalization의 subgroup 안정성 차이를 놓칠 수 있습니다.

ExperimentNormalization확인 목적

BBN running stats freezepretrained 통계 보존 효과
CBN→GN, affine copysmall-batch 독립성

모든 실험에서 seed, augmentation, optimizer, learning rate, scheduler, data split을 동일하게 유지하고 다음을 비교합니다.

  • 전체 Dice / IoU / mAP / sensitivity / specificity
  • small lesion / large lesion subgroup
  • vendor·device·probe·site subgroup
  • validation loss variance와 seed variance
  • calibration / confidence distribution
  • train-eval prediction gap
  • GPU memory, throughput, inference latency
실전 판단: 평균 metric이 같더라도 특정 장비에서 BN 성능이 크게 흔들리고 GN이 안정적이라면 의료 배포 관점에서는 GN의 가치가 클 수 있습니다. 반대로 pretrained BN이 모든 subgroup에서 우수하다면 단순히 batch가 작다는 이유만으로 교체할 필요는 없습니다.

Fine-tuning 시 권장 판단 절차

먼저 원래 구조로 Batch 1~4 Baseline을 확보하고, BN 사용 여부를 확인한 뒤 실제 BN 통계 불안정이 관찰되는 경우에만 Frozen BN, GN, SyncBN을 비교합니다. 새 아키텍처나 처음부터 학습하는 모델에서는 GN이 유효한 후보일 수 있습니다. 사전학습 CNN의 정규화가 원래 없는 곳에 GN/LN을 추가하는 것은 이와 별개의 구조 변경입니다.

평균 Dice/mAP뿐 아니라 작은 병변 Recall, Probe·Vendor·Site별 성능, Seed 변동, Train/Eval 차이, 추론 속도·메모리, 변경 전후 Feature 분포를 함께 검증합니다. 성능을 보장하는 정규화 변경은 없습니다.

10. 복습 문제 8개

  1. BN train과 eval의 가장 큰 차이는?
    train은 current mini-batch statistics를 사용하며 running stats를 갱신하고, eval은 저장된 running stats를 사용합니다.
  2. Gradient accumulation 8회면 BN도 8배 큰 batch 통계를 보나?
    아닙니다. BN은 각 forward의 실제 mini-batch 통계를 봅니다.
  3. BN→GN에서 그대로 옮길 수 있는 것은?
    affine=True일 때 channel별 weight γ와 bias β입니다.
  4. Frozen BN에서 model.train() 호출 후 주의할 것은?
    BN이 다시 train mode가 될 수 있으므로 BN eval 고정을 재적용하거나 Frozen BN 구현을 사용합니다.
  5. GN이 무조건 BN보다 좋은가?
    아닙니다. pretraining, effective batch, domain shift, task와 subgroup validation으로 비교해야 합니다.
  6. 중간 Feature의 64채널은 RGB 색상 64개인가?
    아닙니다. CNN 필터들이 만든 학습된 Feature Map 64개입니다.
  7. 원래 정규화가 없던 모델에 GN을 새로 넣어도 기존 Weight 활용을 보장하는가?
    아닙니다. 로딩은 가능해도 Feature 및 출력 분포가 달라질 수 있습니다.
  8. GPU 메모리 제약으로 Batch Size=2이면 바로 GN/LN으로 바꿔야 하는가?
    아닙니다. 원래 모델의 Baseline 및 BN 통계 문제를 먼저 확인합니다.
