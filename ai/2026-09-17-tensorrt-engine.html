TensorRT Engine
Graph Optimization → Precision → Profiling

TensorRT를 단순 변환 도구가 아니라 target GPU에 맞게 graph와 kernel 선택을 최적화하는 compiler/runtime 관점으로 이해합니다.

1. TensorRT engine은 무엇인가?

TensorRT는 network graph를 분석하고 target GPU에서 사용할 layer implementation(tactic)을 선택해 최적화된 실행 계획을 만듭니다. 따라서 engine은 일반적인 ONNX 파일보다 hardware/software 환경에 더 강하게 종속됩니다.

2. Layer fusion

Conv → normalization → activation 같은 연속 연산은 가능한 경우 더 적은 kernel launch와 memory traffic으로 실행되도록 fusion될 수 있습니다. 속도 향상은 FLOPs 감소뿐 아니라 메모리 이동과 launch overhead 감소에서도 옵니다.

3. FP32 vs FP16

FP16은 memory bandwidth와 tensor-core 활용 측면에서 유리할 수 있지만 모든 layer가 동일하게 빨라지는 것은 아니며 numerical sensitivity도 확인해야 합니다. 정확도 비교 없이 precision만 낮추면 안 됩니다.

4. Dynamic Shape와 Optimization Profile

# 개념 예시
min: (1,1,256,256)
opt: (1,1,512,512)
max: (4,1,768,768)

TensorRT는 동적 입력 범위에 대해 min/opt/max profile을 사용합니다. 실제 workload가 opt shape 근처에 집중되도록 profile을 설계하는 것이 중요합니다.

5. Latency를 올바르게 측정한다

# pseudo benchmark
warmup(50)
synchronize()
start = event()
for _ in range(200):
    infer()
synchronize()
report(p50, p95, throughput)

GPU 연산은 asynchronous이므로 synchronization 없이 CPU wall-clock만 재면 잘못된 결과가 나올 수 있습니다. warm-up, batch size, H/W, precision, transfer 포함 여부를 명시합니다.

6. Memory를 분해해서 본다

weight memory, activation/workspace, input/output buffer를 구분합니다. 특히 high-resolution ultrasound detection에서 P3/P2 feature map이 activation memory를 크게 증가시킬 수 있습니다.

7. Unsupported op → Plugin

TensorRT가 지원하지 않는 operator가 있으면 graph를 지원 연산으로 rewrite하거나 plugin을 구현할 수 있습니다. 이 지점이 이후 CUDA/custom operator 학습과 연결됩니다.

연결: 이전에 ONNX graph에서 unsupported node를 찾았다면 TensorRT에서는 그 node가 parser failure인지, fallback 불가인지, plugin 후보인지 분류합니다.

9. 실습

  1. ONNX 모델의 input shape와 op 목록을 확인합니다.
  2. FP32/FP16 engine을 각각 생성합니다.
  3. warm-up 후 p50/p95 latency를 측정합니다.
  4. 동일 validation subset으로 output/metric 차이를 확인합니다.
  5. profile 또는 profiler에서 가장 느린 layer를 찾습니다.

10. 복습 문제

  1. engine이 ONNX보다 환경 의존적인 이유는? target GPU에 맞는 tactic/optimization이 포함되기 때문이다.
  2. fusion이 왜 빠를 수 있는가? kernel launch와 memory traffic을 줄일 수 있다.
  3. FP16은 항상 안전한가? 아니다, 정확도 검증이 필요하다.
  4. dynamic profile의 opt shape는 무엇을 반영해야 하나? 대표적인 실제 workload.
  5. unsupported op의 대응은? rewrite 또는 plugin.
